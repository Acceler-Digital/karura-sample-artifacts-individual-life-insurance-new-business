# 成果物スキルの作成

## 遵守すべき重要ルール

1. **スキルのファイルだけを作る**: 出力は対象スキルの SKILL.md と template.md に限る。例外は次の 3 つだけとする。スクリプト・成果物本体(`docs/` 配下)は作らない。
   - 成果物が種類の違うファイル(入口ファイルと章ファイル 等)で構成されるなら、template.md の代わりに種類ごとの `template-<種類>.md` を置く。
   - 図の記法のように、文で書くより見本で示すほうが確実な規律があり、§2 でユーザーが見本を置くと決めたなら、`example.md` を置く。
   - CLAUDE.md §8 への略号の追記。
2. **決定はユーザーに委ね、事実は自分で調べる**: 上流・粒度・分割単位・重要ルールなどの判断はユーザーに聞き返して決める。既存のパス・ID・略号・成果物の中身のように調べれば分かることは、ユーザーに聞かない。
3. **引数で指定したスキルだけを扱う**: 他の既存スキルは、型が古くても書き換えない。

## インプットする成果物

| 成果物のパス | 内容 |
|---|---|
| `CLAUDE.md` | §4 の SKILL.md の章構成と責務分担、§8 の略号表、§10 の description の書き方、§11 のフェーズの抽象度 |
| `.claude/skills/*/SKILL.md` | 既存の成果物スキル。カテゴリと上流の推定、スキル名・略号の重複確認に使う。対象成果物を参照している下流スキルからは、下流が本成果物の何をどう引くかを読む |
| `.claude/skills/<上流のスキル>/template.md` | 上流成果物が定義する ID と表の列。関連 ID 列の設計に使う |
| `docs/<上流のフェーズ>/**/*.md` | 上流成果物の実物。ID の実例と分量から、粒度と分割単位の推奨案を作る |
| `docs/<対象のフェーズ>/**/<対象の成果物>` | 対象成果物の実物(スキルより先に存在する場合だけ)。推奨案の起点にする |
| `sidebars.ts` | フェーズのカテゴリ名。生成するスキルのサイドバー登録手順に使う |

## アウトプットする成果物

| 成果物のパス | 内容 |
|---|---|
| `.claude/skills/<スキル名>/SKILL.md` | 対象の成果物スキル |
| `.claude/skills/<スキル名>/template.md` | 対象の成果物のテンプレート(種類ごとに分けるときは `template-<種類>.md`) |
| `.claude/skills/<スキル名>/example.md` | 記法の見本(§2 で置くと決めたときだけ) |
| `CLAUDE.md` | §8 の略号表への追記(ID を振る成果物で、略号が未登録のときだけ) |

## アウトプットに使用するテンプレート

| テンプレートのパス | 内容 |
|---|---|
| `.claude/skills/create-artifact-skill/template.md` | 成果物スキルの SKILL.md の骨組み |

## 引数

| 引数 | 必須 | 意味 |
|---|---|---|
| 成果物名(和名) | 必須 | スキルを作る、または直す対象の成果物の名前 |
| 内容 | 必須 | 新規作成では、成果物に何を書きたいかを自然文で書いたもの。更新では、変えたい点を自然文で書いたもの |
| カテゴリ | 任意 | 成果物のフェーズ(D0〜D11) |

## 処理

### 新規作成

成果物名に対応するスキルが `.claude/skills/` に無いときに行う。対応は、既存の SKILL.md の `# D<N>: <成果物名>` 見出しと description で判断する。

#### 1. 位置づけを推定する

既存スキルの description と出力パス、上流成果物の実物を読み、次の案を作る。案は聞き返しの 1 ラウンド目でまとめて示す。

- カテゴリ: 引数にあればそれに従う。無ければ内容と既存スキルの並びから推定する。もし `docs/` に該当フェーズのディレクトリがまだ無いなら、ディレクトリ名とサイドバーのカテゴリ名も案に含める。成果物フロー(D0)を推定に使いたいなら、先に参照してよいかをユーザーに確認する。
- 上流成果物: 内容が前提にしている情報を出力している既存成果物を挙げ、それぞれの役割を次のどれかに分ける。役割が無い成果物はインプットに入れない。
  - 定義元: 本成果物の行・ID を生む上流。その上流の全 ID を網羅させるかどうかも決める
  - 判定根拠: 載せる/載せない、分ける/まとめるを判定するために読む章
  - 参照: ID の存在確認や文面の補足だけに使う
  - まだ無い確定元: 本成果物で決めきれない判断を後で確定させる成果物(ADR 等)。「想定パス・未作成」としてインプットに入れる
- スキル名と出力パス: スキル名は `d<N>-<成果物の英語名>`(kebab-case)、出力パスは `docs/<フェーズのディレクトリ>/<成果物の英語名>.md` を基本とする。もし同種の成果物をまとめるサブディレクトリ(例: `domain-requirements/`)が既にあるか、成果物をドメイン別・アクター別などに分けるなら、サブディレクトリ配下のパスを案にする。ファイル名・ディレクトリ名は Docusaurus のルーティングを壊さない形にする(数字で始めない、半角の丸括弧を含めない 等)。上流の名称からファイル名を作る成果物では、その変換規則も案にする。
- ID: ID を振る成果物かどうか、振るなら略号とカテゴリの案を示す。もし §8 に当該成果物の略号が登録済みなら、それをそのまま使う。そうでないなら、§8 の既存略号と重ならない略号を案にする。
- 対象成果物の実物: もし `docs/` に対象成果物の実物が既にあるなら、次の手順で案の起点にする。
  1. 章・表の列・ID・数値基準(件数・閾値 等)に加え、慣習(命名・並び順・ファイル名の付け方、図なら記法・配置・線の向き)を読み取る。
  2. 案のルールだけでは再現できない実物の判断(行をまとめた/分けた理由、載せていない上流 ID 等)を列挙し、根拠を上流に探す。
  3. 根拠が見つからない判断と、実物・引数の内容・CLAUDE.md §8 のあいだで食い違う箇所は、どれに合わせるかを §2 で聞く。

#### 2. 聞き返す

決めるべきことをラウンドに分けて聞く。各ラウンドでは、すでに答えられる質問をすべてまとめて番号付きで出し、それぞれに推奨案を添える。質問は「はい」で推奨案を採れる形で書く。前のラウンドの答えに左右される質問は次のラウンドに回す。

聞く内容は次のとおり。

- 位置づけ: §1 で作った案(カテゴリ・上流とその役割・スキル名・出力パス・ID 略号)
- 成果物の形: 1 ファイルか、ドメイン別・アクター別などに分けるか。章立て文書・表・図のどれを主体にするか。表の列。選択肢が決まっている列は、その選択肢
- 分割・集約の単位: 次を分けて聞く
  - 単位の定義(1 行・1 図・1 ファイルが何に当たるか)
  - まとめる原則と、分ける条件・分けない条件
  - 単位に満たないため載せない対象
  - 1 単位あたりの分量の目安・上限と、超えたときの扱い
- 載せないもの・作らない判断: 成果物の中で描かない要素・引かない関係、上流に無い判断を作らないための禁止事項
- 隣接成果物との境界: 本成果物に書かないことと、その振り分け先(上流・下流・並列の成果物)。紛らわしい項目は、どの章・どの成果物に置くかを個別に挙げる
- 表現の規律: 図を含む成果物なら、記法・配置・線の向き・ラベル・命名。文章主体なら用語や表記の揃え方。見本(`example.md`)を置くかどうか
- 下流と外部の制約: 本成果物を受け取って使う下流の作業・外部ツール(Figma 等)と、そのために守ること。準拠する外部の規格・フレームワーク(版・値域・表記の引き写し方)
- 遵守すべき重要ルール: 破ると成果物や下流が壊れる条件
- 新規作成・更新の手順のうち、上流を読んでも決まらない判断(上流に根拠が無い行を落とすか仮置きで立てるか 等)
- 完成時に突き合わせて確かめる対象

決めることが残っていなければ聞き返しを終え、決まった内容をまとめて示し、ユーザーの了承を得てから書く。

ユーザーが「おまかせ」と答えた項目や答えが出なかった項目は推奨案で埋める。そのうち、上流・下流・実物から一意に導けない判断にだけ、生成する SKILL.md の該当箇所に要確認マーカーを付ける。事実から決まる項目(パス・既存の略号 等)には付けない。マーカーを付けられない箇所(description 等)の推奨案は、書き終えた後の報告でユーザーに示す。

#### 3. SKILL.md を書く

テンプレートに従って書く。テンプレート冒頭のコメントは出力に含めない。

- もし上流成果物が無いなら、テンプレートの上流前提の箇所を次のように置き換える。
  - インプット章: 表を置かず「上流成果物は無い。ユーザーへのヒアリングで起こす。」の 1 文にする。
  - description の発火条件: 「プロジェクト立ち上げ時」など、成果物を起こす契機にする。
  - 「新規作成」: ユーザーへのヒアリング手順を入れる。§2 と同じラウンド制を基本とするが、Claude が推奨案を作れない事実(社名・期日・予算・既存システム 等)は、値だけ書き換えて返せる記入用フォームで聞く。
  - 「更新」: ユーザーから変えたい点を聞き取り、その章と、その章を根拠に書いた章だけを見直す手順にする。
- そうでないなら、上流から直接生成する手順にし、「更新」には上流の変更に関わる箇所だけを見直す手順を書く。
- インプット表の「内容」には、§1 で決めた上流の役割と、引く章を書く。
- 「更新」には、ID の採番・欠番の扱いも書く。
- §2 で決めた境界・載せないもの・表現の規律・下流と外部の制約は、破ると下流が壊れるものを重要ルールに、判断の手順を処理に書く。
- 受け取る引数がある場合だけ、「アウトプットに使用するテンプレート」と「処理」の間に「引数」の章を置く。

#### 4. template.md を書く

- 冒頭の HTML コメントは次の 1 行だけにする。

  ```markdown
  <!--
  振る舞いルールは `.claude/skills/<スキル名>/SKILL.md`、汎用規約はリポジトリ直下の `CLAUDE.md` を参照
  -->
  ```

- 本体には、§2 で決めた章・表の列・図の骨格と、プレースホルダ行だけを書く。選択肢が決まっている列は、プレースホルダに選択肢を書く(例: `{{自社別システム / 外部サービス}}`)。
- 成果物側で未確定事項を書く要確認ブロックを毎回置く成果物なら、その枠を置いてよい。§2 の「おまかせ」に由来するマーカーは template に書かない。
- 種類ごとに分ける場合は、各 `template-<種類>.md` に同じ冒頭コメントを置く。

#### 5. 略号を登録する

ID を振る成果物で、略号が §8 に未登録なら、CLAUDE.md §8 の略号表に 1 行追記し、「ID 先頭でカテゴリ判別」の列挙にも略号を加える。

### 更新

成果物名に対応するスキルが `.claude/skills/` にあるときに行う。

1. 対象スキルの SKILL.md と template.md、もしあれば成果物の実物を読む。
2. 変えたい点を反映するうえで決まらないことを、新規作成 §2 と同じ形で聞き返す。
3. 変えたい点を SKILL.md と template.md に反映する。
4. もし対象スキルの章立てが CLAUDE.md §4 の章構成と違うなら、同時にテンプレートの形へ寄せ、description も §10 の最小形に直す。寄せるときは、既存の章の内容を「遵守すべき重要ルール」「処理」「完成時のセルフチェック」のどれかへ移す。§4 で書かないとしている内容(位置づけの紹介・下流への伝搬関係・章構成の再掲など)を削る場合は、削る内容を一覧で示してユーザーに確認する。
5. `example.md` や分割テンプレートが同梱されていれば、変えたい点に関わらない限りそのまま残す。
6. もし略号を変えるなら、§8 を直し、その略号を使っている成果物が `docs/` 配下にあることをユーザーに伝える。

## 完成時のセルフチェック

- SKILL.md の章が CLAUDE.md §4 の順に並んでいる
- description が 1〜3 文で、レビュー動作を含まない
- template の冒頭コメントが参照案内の 1 行だけになっている
- インプット表の各行に役割が書かれ、パスが実在する。実在しないパスには「想定パス・未作成」と書いてある
- 追記した略号が §8 の既存の略号と重複していない
- §2 で決めた境界・載せないもの・表現の規律・下流と外部の制約が、SKILL.md の重要ルールか処理のいずれかに書かれている
- template に「おまかせ」由来の要確認マーカーが無い
- SKILL.md に `{{スキル名}}` `{{成果物名}}` など、create-artifact-skill の template.md 由来のプレースホルダが残っていない
